## 2. 两种调用方式

### 2.1 方式 A：命令行 / 子进程（语言无关，推荐给非 Python 前端）

```bat
:: 单张图片，输出 JSON 到 stdout
run_cpu.bat predict.py --source D:\img\part001.png --json

:: 整个文件夹批量
run_cpu.bat predict.py --source D:\img\batch --json --save D:\img\out

:: 结果直接落盘成 UTF-8 JSON，再从代码里读文件
run_cpu.bat predict.py --source D:\img\batch --json-out D:\img\result.json

:: 打开相机实时检测（黑白，按单通道读）
run_cpu.bat predict.py --source 0 --camera --gray
```

> `run_cpu.bat` 只是把参数原样转发给 `runtime_cpu\python.exe`，等价于
> `runtime_cpu\python.exe predict.py <你的参数>`。
> 有 NVIDIA 独显（已装 CUDA 依赖）就把 `run_cpu.bat` 换成 `run_cuda.bat`。

### 2.2 方式 B：Python 模块 import（推荐，性能最好）

```python
import sys
sys.path.insert(0, r"D:\yolo_deploy")          # 指向交付包根目录
from predict import CurtainsDetector

det = CurtainsDetector()                        # 进程内只创建一次！
result = det.predict_frame(gray_frame)          # gray_frame: numpy (H, W) uint8
for d in result["detections"]:
    print(d["class_name"], d["conf"], d["xyxy"])
```

> ⚠️ **`CurtainsDetector()` 一定要在进程启动时创建一次并复用**。
> 首次调用会有 1~3 秒的模型图构建开销，每帧重建会直接拖垮产线节拍。
> 用随包的 `run_cpu.bat` / `run_cuda.bat` 启动你的脚本，即可复用同一个便携环境。

完整可运行示例见 `examples/demo_module_api.py`：

```bat
run_cpu.bat examples\demo_module_api.py
```

## 3. 接口契约

### 3.1 构造参数 `CurtainsDetector(...)`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `weights` | str | `<包根>/model/best.pt` | 权重路径，一般不用传 |
| `device` | str | `"auto"` | `auto` / `cpu` / `cuda` / `cuda:0` / `0`。`auto` = 有 N 卡用 GPU，否则 CPU |
| `conf` | float | `0.37` | 置信度阈值。**这是现场最需要调的参数** |
| `iou` | float | `0.7` | NMS IoU 阈值。与训练时一致，不建议改 |
| `imgsz` | int | `640` | 推理分辨率。**必须与训练一致，不要改小** |
| `max_det` | int | `300` | 单图最大检出数 |
| `half` | bool | `None` | `None` = 有 CUDA 自动开 fp16，CPU 强制关 |
| `warmup` | bool | `False` | 是否在构造时就预热一次 |

### 3.2 返回结构 `predict_frame(...)`

```json
{
  "detections": [
    {
      "class_id": 1,
      "class_name": "ink",
      "class_name_zh": "墨水/污点",
      "conf": 0.9674,
      "xyxy": [390.2, 20.0, 512.0, 508.0],
      "xywhn": [0.88116, 0.515809, 0.23768, 0.954096],
      "area_px": 59446
    }
  ],
  "num": 1,
  "infer_ms": 34.97,
  "shape": [512, 512],
  "device": "cpu"
}
```

| 字段 | 说明 |
|---|---|
| `class_id` | 0/1/2，与 `class_name` 一一对应 |
| `class_name` | 模型自带类别名，**以这个为准** |
| `class_name_zh` | 参考中文译名，仅供界面展示，需业务确认 |
| `conf` | 置信度 0~1 |
| `xyxy` | 像素坐标 `[左上x, 左上y, 右下x, 右下y]`，**原点在左上角，未做任何缩放** |
| `xywhn` | 归一化中心点框 `[cx, cy, w, h]`，值域 0~1；要按百分比算面积就用它 |
| `area_px` | 框面积（像素²），常用于过滤极小的误检 |

`detections` **已按 `conf` 从高到低排好序**，直接取 `detections[0]` 就是最可信的那个。
`num == 0` 表示这一帧无缺陷。

### 3.3 类别表

| class_id | class_name | 参考中文名 |
|---|---|---|
| 0 | `hole` | 孔洞 |
| 1 | `ink` | 墨水 / 污点 |
| 2 | `broken_filament` | 断丝 |

### 3.4 其他常用方法

| 方法 | 用途 |
|---|---|
| `predict_frame(image, save_path=None, gray_bit_shift=None)` | 单帧推理（主接口） |
| `predict_batch(list_of_images)` | 批量，顺序与输入一致 |
| `draw(bgr_image, detections)` | 在图上画框，返回新图（不修改原图） |
| `run_camera(index, gray=True, show=True, limit=0)` | 直接开相机跑实时循环 |
| `benchmark(rounds=20)` | 性能测试，返回 ms/帧 与 FPS |
| `info()` | 打印环境与模型信息，排查问题用 |

## 4. 黑白相机对接（重点）

### 4.1 结论：灰度帧直接喂进去就行，不用做任何额外处理

训练集是「**灰度内容存成三通道 PNG**」，即 R=G=B 逐像素完全相等（已逐图核验，180/180 张全部成立）。
所以现场 Mono8 黑白相机拿到的单通道帧，只要在内部做一次 `GRAY2BGR` 复制三通道，就与训练分布**完全对齐**。

`predict_frame()` 已经内置处理：

```python
det.predict_frame(gray)                            # HxW uint8 单通道，最常用
det.predict_frame(gray16, gray_bit_shift=8)        # HxW uint16，右移 8 位
det.predict_frame(bgr)                             # HxWx3 BGR，也支持
```

支持的输入：`HxW`（灰度）、`HxWx1`、`HxWx3`（BGR）、`HxWx4`（BGRA）、`uint8/uint16/float`、图片路径、图片字节流。

### 4.2 相机侧必须确认的三件事

| 检查项 | 要求 | 说明 |
|---|---|---|
| **像素格式** | 设为 `Mono8`（8 bit 单通道） | 这是最省事、也是与训练最匹配的配置 |
| **分辨率** | 尽量接近 512×512 | 训练图全部是 512×512。现场分辨率和长宽比差异太大会影响精度 |
| **黑白极性** | 缺陷呈「亮」或「暗」需与训练数据一致 | 训练图缺陷在灰度上的明暗倾向需业务侧比对 |

如果相机只能出 16 bit（Mono12/Mono16）：

```python
# 默认右移 8 位（等价 /256）。若有效数据只有 12 位（值域 0~4095），用 gray_bit_shift=4
det.predict_frame(frame16, gray_bit_shift=8)
```

> ⚠️ **位深转换这一步必须现场实测确认**。选错位移量会让图像整体过暗或过曝，直接导致漏检。
> 建议：先用 SDK 存一张现场实拍图，再分别用 `gray_bit_shift=0/4/8` 跑一遍，肉眼比对哪种最接近正常灰度。

### 4.3 用厂商 SDK（海康 / 大恒 / Basler）取帧的写法

```python
from predict import CurtainsDetector

det = CurtainsDetector(device="auto")      # 只创建一次

# --- 用厂商 SDK 代替 cv2.VideoCapture ---
# 海康 MvCamera / 大恒 GxIAPI / Basler pylon：打开相机，设 Mono8，开始取流
cam = VendorSdk.open_camera(serial="xxxx", pixel_format="Mono8")
cam.start_grabbing()

while running:
    frame = cam.get_frame()                # numpy (H, W) uint8 单通道
    result = det.predict_frame(frame)
    if result["num"] > 0:
        on_defect(result["detections"])     # 你的业务：报警 / 打标 / 存图 / 记录
    else:
        on_pass()

cam.stop_grabbing(); cam.close()
```

用 OpenCV 打开的 UVC 相机（调试用）：

```python
import cv2
cap = cv2.VideoCapture(0, cv2.CAP_DSHOW)
cap.set(cv2.CAP_PROP_CONVERT_RGB, 0)       # 关键：请求原始单通道，不要让 OpenCV 转成彩图
# 或者直接用现成的：run_cpu.bat predict.py --source 0 --camera --gray
```

### 4.4 相机对接常见坑

1. **OpenCV 默认把灰度图转成三通道 BGR 返回**。这不会出错（三通道内容仍是灰度），但会白白损失一份内存拷贝。用 `CAP_PROP_CONVERT_RGB=0` 可以拿原始单通道。
2. **不要做直方图均衡 / 自动对比度 / 锐化**。训练数据没有这些增强，加了反而引入分布偏移。
3. **不要缩放后送入**。`imgsz=640` 由模型内部按 letterbox 处理，外部再缩放会二次失真。
4. **相机曝光、增益、光源要与采集训练数据时保持一致**。这是现场精度波动最大的来源。
5. 如果相机 SDK 给的是 `HxW` 但 dtype 为 `uint16`，务必走 4.2 的位深处理，不要直接 `astype(uint8)`（会把高位截断成噪声）。

## 5. 性能数据

本机实测（512×512 输入，`imgsz=640`，warmup 后取 30 次平均）：

| 环境 | 设备 | 平均耗时 | 折算帧率 |
|---|---|---|---|
| `runtime_cpu` | CPU（AMD 32 线程） | 约 34 ms/帧 | 约 29 FPS |
| CUDA（torch 2.5.0+cu118，需自行安装） | NVIDIA RTX 4060 Laptop（fp16） | 约 10.5 ms/帧 | 约 95 FPS |

GPU 相比 CPU 约 **3.2 倍**提速，且 `--device auto` 会自动选择，无需改代码。

> 现场 CPU 通常弱于测试机，**CPU 路径实测请以现场 `--benchmark` 结果为准**。
> 产线节拍要求高于 15 FPS 时建议上 NVIDIA 独显。

**首次调用约需 1~3 秒**（模型图构建），之后每帧稳定在毫秒级。
生产代码里务必用 `CurtainsDetector(..., warmup=True)` 在启动阶段吃掉这段开销。

调节手段（按代价从低到高）：

- `conf`：调高减少误检、调低提高召回。**现场首要调参项**。
- `half=True`（仅 CUDA）：约提速 30~50%，精度影响很小。
- `imgsz`：**不建议改**。改小会明显掉精度，改大会变慢且与训练分辨率不一致。

## 6. 常见问题排查

| 现象 | 原因与处理 |
|---|---|
| `找不到便携 Python 环境` | `runtime_cpu/` 文件夹没跟 `run_cpu.bat` 放一起，或拷贝时被漏掉；也可安装系统 Python 后重试 |
| `找不到权重文件` | `model/best.pt` 缺失，用 `--weights` 指定实际路径 |
| 输出中文乱码 | 用 `run_cpu.bat` 启动（已设 `chcp 65001` + `PYTHONUTF8=1`）；直接调 python.exe 时需自行设这两个 |
| `ImportError: DLL load failed while importing _C: 找不到指定的模块` | **目标机缺 VC++ 运行库 `msvcp140.dll`**（不是 torch 装错）。见下方 6.1 |
| `指定了 CUDA 设备，但检测不到可用的 NVIDIA GPU` | 换 `--device cpu`，或装匹配的 NVIDIA 驱动（CUDA 11.8 需驱动 ≥ 522.06） |
| 第一次调用卡几秒 | 正常，模型图构建。用 `warmup=True` 提前消化 |
| 相机打不开 | 先确认相机没被其他程序占用；厂商相机需用其 SDK，不能直接 `cv2.VideoCapture` |
| 检测框很多但都很像误检 | 调高 `conf`（如 0.4~0.5）；或用 `area_px` 过滤过小框 |
| 完全检测不出缺陷 | 见下文第 7 节「已知限制」——**这是当前模型本身的能力问题，不是集成问题** |

### 6.1 目标机报 `DLL load failed ... _C` 时的处理

torch 的所有 DLL 都依赖微软 **`MSVCP140.dll`**（VC++ 2015-2022 运行库），
而 Python 便携包只自带 `vcruntime140.dll`，**不含 `MSVCP140.dll`**。
干净安装的 Windows 10 有可能没装这个运行库，表现就是 `import torch` 直接失败。

处理办法（**只需做一次，永久有效**）：

1. 在目标机上装一次微软官方的 **Microsoft Visual C++ 2015-2022 Redistributable (x64)**
   下载页：`https://aka.ms/vs/17/release/vc_redist.x64.exe`
2. 装完重跑 `run_cpu.bat predict.py --selfcheck`，看到 `[OK] 自检通过` 即可。

> 判断方法：如果 `--selfcheck` 在 `[2/5] torch` 这一步就崩，而不是在模型加载阶段，基本可以确定是这个原因。
> 也可以直接看目标机 `C:\Windows\System32\msvcp140.dll` 是否存在，不存在就是缺。

## 7. 已知限制（集成前务必阅读）

### 7.1 模型精度偏低，当前版本不建议直接作为产线唯一判据

本次交付的 `best.pt` 训练指标（最佳轮次 epoch 21）：

| 指标 | 数值 |
|---|---|
| Precision | 0.484 |
| Recall | 0.419 |
| mAP@50 | **0.290** |
| mAP@50-95 | 0.114 |

训练只跑到第 31 轮就因 `patience=10` 早停（配置是 500 轮），训练集仅 **108 张**。

### 7.2 三个类别中，实际上只有 `ink` 能稳定检出

在验证集 + 测试集（72 张）上实测：**60 张有检出，全部为 `ink`；`hole` 和 `broken_filament` 一次都没有被检出。**

根因是训练数据类别严重不平衡：

| 数据集 | ink | hole | broken_filament |
|---|---|---|---|
| train（108 张） | 168 框 | 18 框 | 24 框 |
| val（54 张） | 89 框 | 9 框 | 12 框 |
| test（18 张） | 30 框 | 3 框 | 3 框 |

`ink` 占了约 80%。**如果产线必须检出孔洞和断丝，当前模型无法满足**，需要补数据重训。

### 7.3 建议的下一步

1. 优先补充 `hole` 与 `broken_filament` 的样本（各类目标至少数百框），重训后再交付产线。
2. 现场先用 `ink` 单类做试运行，同时记录真实过检情况，反哺数据集。
3. 重训后**接口不变**，只需替换 `model/best.pt`，`predict.py` 与前端代码无需改动。

### 7.4 环境一致性已验证

交付包的便携环境与训练环境（anaconda `envs/yolo`）在 **CPU fp32 下逐位一致**（置信度与坐标完全相同，已在 `samples/` 三张图上交叉验证）。
CUDA 版跑 CPU 与 CPU 版跑 CPU 的结果同样逐位一致。
GPU fp16 与 CPU fp32 的差异在 0.4 像素 / 0.002 置信度以内，检出数量完全一致，属正常浮点差异。
